## Жёсткие правила

1. **Один файл — одна программа.** `package main`, единственная функция
   `main`, все вспомогательные функции и типы — в том же файле.
2. **Скелет компилируется.** `main.go` для задач «напиши с нуля» должен
   собираться, даже если печатает `TODO`. Заглушки типов и функций
   добавляй в скелет. Исключение — задачи «исправь ошибку»: там код
   намеренно сломан.
3. **Вывод программы — только ASCII.** Никаких русских строк в `fmt.Print`.
   Русские комментарии в коде допустимы: файлы в UTF-8.
4. **Точный вывод.** Тесты сравнивают байты после нормализации
   `\r\n` → `\n`. В README явно указано, есть ли перенос строки в конце.
   `fmt.Println` = `\n`, `fmt.Print` = без `\n`.
5. **Никаких комментариев в `solution.go`.** Как в Школе 21. Комментарии —
   только в `solution_commented.go` и в `// TODO` скелета.
6. **Стиль.** Табы (как `gofmt`), `gofmt`-совместимое форматирование,
   K&R-скобки. Проверяй: `gofmt -l .` не должен ничего выводить.
7. **Детерминированный вывод.** Не полагайся на порядок обхода `map` и
   планировщик горутин. Сортируй ключи, синхронизируй каналы.
8. **Крайние случаи в тестах.** Пустой ввод, `n = 0`, отрицательные числа,
   деление на ноль, отсутствующий файл.

## `run_testsN_M.sh` — шаблон

```bash
#!/usr/bin/env bash
set -e
cd "$(dirname "$0")"
source ../../../scripts/lib.sh

compile

run_case "2 2" $'4\n'
run_case "-4 4" $'-16\n'
run_case_devnull $'0\n'

if [ -z "$FAILED" ]; then
  echo "Все тесты пройдены"
else
  echo "Есть проваленные тесты"
  exit 1
fi
```

### API scripts/lib.sh

- `compile` — собирает `$SOURCE_FILE` (по умолчанию `main.go`) в `.build/`.
  Дополнительные флаги `go build` передаются аргументами.
- `run_case "вход" "ожидание"` — вход через `printf` (добавляет `\n`).
- `run_case_noeol "вход" "ожидание"` — без завершающего `\n`.
- `run_case_devnull "ожидание"` — пустой stdin (EOF сразу).
- `run_case_args "аргументы" "вход" "ожидание"` — запуск с аргументами.

Ожидание — точные байты:

```bash
run_case "2 2" $'4\n'          # Println
run_case "2 2" "4"             # Print
run_case $'a\tb\nc' $'3\n'     # табы и переводы строк
```

### Файловые задания

Создай файлы до вызова `run_case` и удали их через `trap`:

```bash
trap 'rm -f input.txt output.txt' EXIT
printf 'hello\n' > input.txt
run_case "input.txt" $'hello\n'
```

Относительные пути считаются от папки задания.

## Порядок проверки

```bash
cd tasks/<раздел>/<задание>
SOURCE_FILE=solution.go bash run_testsN_M.sh
SOURCE_FILE=solution_commented.go bash run_testsN_M.sh
rm -rf .build
```

Оба запуска должны напечатать `Все тесты пройдены`.

Проверка скелета:

```bash
SOURCE_FILE=main.go bash -c 'source ../../../scripts/lib.sh; compile'
```

Для задач «исправь ошибку» эта команда может падать — это ожидаемо.

Проверка форматирования:

```bash
gofmt -l .
```

Список файлов должен быть пустым.

## theory.md — что писать

Хороший разбор содержит:

1. **Идею** — зачем нужна тема, где пригодится.
2. **Минимальный пример** на Go в `~~~go`.
3. **Разбор** — что делает каждая строка.
4. **Таблицу** сравнения или шпаргалку.
5. **Частые ошибки** — 3–5 пунктов с последствиями.
6. **Крайние случаи** — что будет при `0`, `nil`, пустой строке.

Не пересказывай учебник. Пиши то, что нужно именно для этого задания.

## Генератор из спецификаций

Все 71 задание собраны из `specs/*.spec` скриптом `build.js`. Спецификация
удобна для массового создания заданий: в ней нет JS-экранирования, Go-код
и Markdown лежат как есть.

Формат спецификации:

```text
@@TASK
section: 05_slices
dir: 01_slice_sum_average
num: 5_1
title: GO_05_01. Сумма и среднее
topics: срезы, `append`, `len`
input: Число N, затем N целых чисел
@@DESC
...
@@EXAMPLES
| Входные данные | Результат работы |
| ------ | ------ |
| 3<br>1 2 3 | Sum: 6 |
@@THEORY
...
@@TESTS
| `3\n1 2 3` | `Sum: 6\n` |
@@CASES
run_case $'3\n1 2 3' $'Sum: 6\n'
@@MAIN
package main
...
@@SOLUTION
package main
...
@@COMMENTED
package main
...
@@END
```

Пересборка:

```bash
node build.js
```

Генератор — внутренний инструмент. Для прохождения заданий он не нужен.
Если правишь задание вручную, помни: следующая сборка перезапишет файлы
из спецификации.
